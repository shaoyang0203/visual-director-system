# 内部骨架与用户交互

六步不是六轮问答。第一步就识别硬要求，第五步复核自由度，不是第五步才开始保真。
第二至四步可以因依赖返回，仍共享当前协调预算。

用户路径：
正常三套构思 → 选择方向 → 完整母版 → 明确确认版本 → 编译和最终复核 → 交付。
修改已确认画面：登记用户修改 → 局部设计及依赖复核 → 新母版完整展示 → 确认新版本 → 重编译。
修改明确要求时不得只在英文稿替换名词。

人物情境：识别身份、时代和开放项。
瞬间主题：确定当前状态和真正视觉主体。
环境关系：确定支撑、接触、距离、朝向及环境反馈。
视觉设计：人物美术阶段共同决定可见面部特征、妆容与发型，补充有依据的肤质和当下状态；具体选择进入母版，知识备选与职业推断不进入成品。基础检查常驻；只对未解决的专业问题查阅或复用知识。已知ID直接读取，未知才搜索；同一关系不重复堆写。
约束复核：用户决定越多，新增设计幅度越小，完成质量不降低。
编译验收：缺失关键设计退回相应步骤，不能在编译时补画面。

文本模式在对话维护 JSON 及版本；工具模式用本地快照。
两者都不能把未确认、fail 或 uncertain 变成最终成品。

## 两类任务的表达粒度

已有提示词优化：把原文作为信息基线，整理、消歧、归并重复；保持其宽泛或具体的程度。完整构思探索仅用于用户要求新创作或重新设计的任务。重大歧义需要确认，不靠自动补细节掩盖冲突；设计变更仍走原母版确认流程。
从零创作：按既有六步完成设计，补充有具体用途的事实，开放项可留白。九区域完整展示不等于九区域都要有独立新增项。
两类任务都先归并已确认事实，再编译正文，最后按全部设计项检查覆盖。检查清单可以逐项，成品不按清单逐项复述。具体方法见[紧凑编译](compiler-contract.md#紧凑编译)。
